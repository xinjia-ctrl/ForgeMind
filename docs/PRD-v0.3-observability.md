# ForgeMind 第三轮产品需求文档（PRD v0.3）

> 迭代：第三轮 — 可观测性可视化（Phase 2）
> 前置：第一轮 MVP 闭环（v0.2）已实现；第二轮质量门禁 + 可复现性为工作区改动
> 状态：P0 已实现（31/31 测试通过）；P1 延后

---

## 1. 产品定位（本轮视角）

ForgeMind 已经能做到"一条需求 → 一个 commit"，但过程是不可见的：Agent 之间如何协作、为何返工、门禁为何驳回、token 消耗在哪里，使用者只能读 JSONL。

**本轮要解决的核心问题**：把"不可见的多 Agent 协作过程"变成**可播放、可解释、可定位**的视觉叙事。

这既是面试演示的杀手锏（把编排能力"演出来"），也是开发者排障的刚需（3 秒定位失败发生在哪个 Agent / 门禁 / 工具）。

## 2. 目标用户与场景

| 场景     | 用户     | 核心诉求                                                                                  |
| -------- | -------- | ----------------------------------------------------------------------------------------- |
| 面试展示 | 候选人   | 运行结束后一键生成可视化报告，逐步播放 6 阶段协作过程，展示门禁如何拦截缺陷、返工如何发生 |
| 失败排障 | 开发者   | 定位一次失败 Run 发生在哪个阶段、哪个门禁、哪个工具，原因是什么                           |
| 过程审计 | 研发团队 | 快速概览一次 Run 的全貌：阶段耗时、token 消耗、门禁判定、产物清单                         |

## 3. 核心能力

### P0（本轮必做）

1. **时间线可视化**：以时间为轴展示一次 Run 的全部事件——6 阶段推进、attempt 编号、门禁通过/驳回、LLM 调用、工具调用、产物产出。
2. **一键生成报告**：Run 结束后（或对任意历史 `run-id`）生成一份可打开的可视化报告，无需起服务、无需联网。
3. **门禁裁决高亮**：REVIEW 驳回 / TEST 失败用显著状态标识，展示返工回路（驳回 → CODE 返工 → 再审查）的完整循环。
4. **失败定位视图**：Run 失败时，报告首屏直接指向失败阶段、失败类型（Stage/Hard/Fatal）、错误信息与现场证据。
5. **阶段汇总统计**：每阶段 token 消耗（input/output）、工具调用次数、耗时，支撑"上下文预算控制"的可视化证明。

### P1（本轮力争，可延后）

6. **实时运行视图**：Run 进行中通过终端/界面实时滚动事件流（探索态，后端已具备事件订阅条件）。
7. **可复现性对照展示**：同一需求两次 Run 的流程签名对比，可视化展示"同输入 → 同流程"。

## 4. 产品形态决策（已采纳方案 A）

| 方案                                                              | 优点                               | 缺点                                       | 建议                                  |
| ----------------------------------------------------------------- | ---------------------------------- | ------------------------------------------ | ------------------------------------- |
| **A. 静态 HTML 报告**（从 JSONL 生成单文件 HTML，浏览器直接打开） | 零服务、零依赖、离线可用、演示最稳 | 无实时性；报告为快照                       | ✅ **推荐**，契合"一键生成"与面试演示 |
| B. 本地 Web 服务 + 前端                                           | 支持实时刷新、交互更强             | 引入 Node 服务与端口管理，演示多一步失败面 | 作为 Phase 2 后半段可选增强           |
| C. 终端 TUI                                                       | 复用 Node 生态、geek 感强          | 视觉效果弱于 Web，说服力不足               | 不推荐为主形态                        |

> 已采纳 A：报告即产物（`<git-dir>/forgemind/reports/<run-id>.html`），与现有"事件日志是唯一事实源"的架构天然契合——**报告是日志的投影，不是第二份事实**。

## 5. 非目标（本轮不做）

- 不做跨项目长期记忆（仍为 Phase 4）。
- 不做并发任务与多项目并行管理。
- 不做在线编辑 / 从报告发起重跑（只读展示）。
- 不做沙箱执行与审批网关（Phase 3）。

## 6. 演示验收标准（DoD）

给定一次真实 Run（含一次成功与一次人为失败用例），必须同时满足：

- [x] 一条命令（`forge-mind report --repo <path> --run-id <id>`）生成单文件 HTML 报告；
- [x] 报告展示 6 阶段推进、attempt 编号、门禁通过/驳回状态；
- [x] 失败 Run 报告首屏可直接定位失败阶段与原因；
- [x] 报告含每阶段 token 消耗与工具调用统计；
- [x] 报告离线可打开（无网络、无服务依赖）；
- [x] 报告生成逻辑纯函数化，并由单元测试覆盖（事件 → 视图模型 → 渲染）。

## 7. 与既有能力的衔接（无需新架构）

| 已具备                                      | 本轮利用方式             |
| ------------------------------------------- | ------------------------ |
| `EventLog` JSONL（版本化事件）              | 报告的数据源，零改动     |
| `replay()` 纯函数回放                       | 复用其事件归一化逻辑     |
| `workflowTrace / workflowSignature`（v0.2） | 报告时间线的基础视图模型 |
| 三层失败分类（Stage/Hard/Fatal）            | 失败定位视图的状态映射   |

## 8. 风险与评审要点

1. **数据敏感**：事件日志含工具调用参数与审计脱敏后的内容。报告渲染必须复用现有 `auditValue` 脱敏，禁止把原始 prompt/token 泄露进报告。
2. **报告体积**：长 Run 事件多，HTML 需限制渲染条目（如仅渲染归一化视图 + 抽样展开），避免演示卡顿。
3. **"可视化"不变成"糊"**：产品纪律——报告只呈现**已有事件**，不编造指标。所有统计必须能追溯到具体事件行。
4. **工作量边界**：若 P1 实时视图超出预算，本轮交付 P0 静态报告即达标，实时能力明确划入 Phase 2 后半段。
