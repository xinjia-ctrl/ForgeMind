# ForgeMind 第四轮产品需求文档（PRD v0.4）

> 迭代：第四轮 — 生产级安全与沙箱（Phase 3）
> 前置：v0.3 已实现（MVP 闭环 + 可观测性报告，31/31 测试通过）
> 状态：P0/P1 已实现（45/45 测试通过）

---

## 1. 产品定位（本轮视角）

前三轮已解决"能不能做"（闭环）与"看不看得见"（可观测）。但产品仍有一个明确的边界让步：`run_command` **直接在本机执行**，只在白名单命令约束下运行。这使其只能用于受信任的演示仓库，无法交付给真实用户。

**本轮要解决的核心问题**：把"仅限受信任仓库的演示工具"升级为"可在真实项目上安全运行的生产级工具"——任何代码执行都被隔离在沙箱中，危险动作需要人类审批，全流程可审计。

这同时是产品可信度的分水岭：**从"面试 Demo"到"敢在真实项目上跑的工程系统"**。

## 2. 目标用户与场景

| 场景         | 用户              | 核心诉求                                                                     |
| ------------ | ----------------- | ---------------------------------------------------------------------------- |
| 真实仓库接入 | 开发者            | 在自己的项目上放心跑 ForgeMind，不用担心 Agent 执行了危险命令                |
| 团队落地     | 研发团队 / 管理员 | 可配置哪些工具/命令需要人工审批，安全策略可审计、可追溯                      |
| 面试展示     | 候选人            | 展示"生产级安全设计"——沙箱隔离、审批网关、最小权限，是高级架构师级别的加分项 |

## 3. 核心能力

### P0（本轮必做）

1. **沙箱执行**：`run_command` 的测试执行从"本机直接跑"迁入隔离沙箱，Agent 无法直接访问宿主机文件系统、网络与进程。
2. **审批网关**：对高风险动作（`run_command`、`git_commit`、模型外网络请求等）引入"需审批"策略；未批准即拒绝，拒绝结果进入审计日志。
3. **最小权限策略**：每阶段的可写范围、工具白名单、命令白名单从"代码内硬编码"升级为**可配置**（配置文件 / 环境变量）。
4. **权限模式**：至少支持 `allow（自动放行）/ approve（需人工审批）/ deny（禁止）` 三态，可配置在仓库/项目/全局级别。
5. **安全审计视图**：所有审批决策（谁、何时、批了什么、结果）进入 EventLog，并通过 `forge-mind report` 展示"安全事件"面板。

### P1（本轮力争，可延后）

6. **沙箱资源上限**：CPU / 内存 / 超时 / 输出字节的沙箱内硬限制，防止 Agent 失控。
7. **审批 CLI 交互**：运行中遇到需审批动作时，终端交互式询问（`y/n`）或 `--yes` 自动批准受信任命令。

## 4. 沙箱方案决策（已采纳方案 A）

| 方案                                        | 优点                             | 缺点                                     | 建议                     |
| ------------------------------------------- | -------------------------------- | ---------------------------------------- | ------------------------ |
| **A. 容器（Docker/Podman）沙箱**            | 隔离彻底、业界标准、演示说服力强 | 依赖容器运行时；冷启动开销；需镜像管理   | ✅ **推荐为主方案**      |
| B. 系统级进程隔离（sandbox-exec / seccomp） | 无容器依赖、轻量                 | 平台绑定、配置复杂、隔离不彻底           | 作为无容器环境的降级方案 |
| C. 纯白名单 + 审批（无沙箱）                | 零依赖、实现快                   | 未解决"代码执行"本质风险，安全升级不完整 | 仅作为过渡，不单独立项   |

> 已采纳 A：Docker/Podman 容器沙箱作为生产默认；无容器环境默认拒绝。`sandbox.mode=local` 仅作为显式受信任降级，且强制 `defaultMode=deny`。审批网关作为第一道闸门、沙箱作为第二道防线。

## 5. 非目标（本轮不做）

- 不做长期记忆（Phase 4）。
- 不做并发任务调度（本轮仅保证单任务沙箱化，多任务编排延后）。
- 不做 Agent 自由对话拓扑（仍为顺序流水线）。
- 不做云端托管 / SaaS 化。

## 6. 演示验收标准（DoD）

给定一个真实演示仓库与一次真实 Run，必须同时满足：

- [x] 测试命令通过统一 `ProcessRunner` 在容器沙箱执行，`tool.called` 记录运行时、容器 ID、镜像与资源策略；
- [x] 未配置为自动放行的危险命令被审批网关拦截，未批准不执行；
- [x] 审批请求、批准与拒绝完整写入 EventLog；
- [x] CPU、内存、PID、网络、超时和输出限制进入沙箱/进程执行参数；
- [x] `forge-mind report` 展示安全审计事件（动作、策略、决策、来源、时间）；
- [x] 全流程仍能产出有效 commit，原有 31 项测试与新增测试共 45 项全部通过。

> 自动化验收覆盖完整 Run、容器调用参数与隔离证据；当前开发环境未安装 Docker/Podman，因此真实容器镜像的发布 smoke test 仍需在具备运行时的环境执行。

## 7. 与既有能力的衔接

| 已具备                                                    | 本轮利用方式                                          |
| --------------------------------------------------------- | ----------------------------------------------------- |
| `ToolPolicy`（allowedTools / allowedCommands / writable） | 保留为不可被配置放宽的阶段安全上限，外叠三态策略      |
| `auditValue` 脱敏 + `tool.called` 事件                    | 审批决策作为新事件类型进入 EventLog，报告复用投影管线 |
| `runProcess`（无 shell、超时、输出上限）                  | 作为沙箱内进程执行的宿主接口，参数注入沙箱            |
| `path-safety` 严格校验                                    | 继续保护宿主文件工具；沙箱仅获得工作区只读挂载        |

## 8. 风险与评审要点

1. **容器依赖**：用户环境没有 Docker 时产品不可用。必须提供明确的检测与降级策略（方案 B），并在文档与 CLI 报错中给出指引。
2. **审批体验**：审批网关做不好会拖慢演示、显得繁琐。默认策略必须"最小惊扰"——常规命令自动放行，只有高风险动作才询问。
3. **沙箱一致性**：沙箱内文件系统必须是宿主工作区的只读快照 + 独立可写层，避免"沙箱里改了但宿主没改"的语义漂移。
4. **可复现性回归**：沙箱引入的环境差异（路径、系统库）可能破坏 `workflowSignature` 稳定性。沙箱镜像需固定版本并纳入文档约束。
5. **工作量边界**：P1（资源上限、交互审批）超预算则本轮交付 P0 五项的静态审批模式，实时交互审批明确划入 Phase 3 后半段。
