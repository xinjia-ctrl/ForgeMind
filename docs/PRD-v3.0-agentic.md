# ForgeMind 产品需求文档（PRD v3.0 — 研发操作系统）

> 版本：v3.0（第九轮 — 从企业平台到研发操作系统）
> 前置：v2.0 企业集成 + RBAC + 审计基座已实现
> 状态：A1-A6 已实现，签名事件输入到幂等 Run、PR/评论回写形成完整闭环
> 验证：`npm run check` 通过（151 项：148 通过，3 项真实依赖 smoke 条件跳过）
> 对齐愿景：E1（需求到上线）、E2（审批范式）、E3（记忆资产）

---

## 1. 产品定位（本轮视角）

v0.2–v2.0 建立的是一条**需求驱动的流水线**：人给需求 → ForgeMind 执行 → 产出 PR。人是起点，系统是被动的。

**本轮要解决的核心问题**：让 ForgeMind 从"等人给需求"变为"主动盯住研发流"——像一名常驻研发工程师那样，看到 issue 更新、CI 失败、PR 评论就主动行动，把"人发现 → 人触发"变成"系统发现 → 系统触发 → 人审批"。

这是 VISION 中"研发操作系统"（v3.0）的落地：**前几轮做"能力"，本轮做"主动性"**。系统的价值从"执行工具"升级为"自动维护研发流的运行环境"。

## 2. 目标用户与场景

| 场景       | 用户      | 核心诉求                                                |
| ---------- | --------- | ------------------------------------------------------- |
| 团队日常   | 开发者    | CI 挂了自动诊断、issue 标签了自动出方案，少一次手动搬运 |
| 主动式交付 | Tech Lead | 需求从 issue 到 PR 全自动，人只做关键审批               |
| 无人值守   | 平台团队  | 夜间/周末系统自主处理常规任务，且全部可审计、可回滚     |
| 面试展示   | 候选人    | 展示"事件驱动 + 主动式 Agent + 安全护栏"的系统级能力    |

## 3. 核心能力

### P0（本轮必做）

**A1 主动监测（Watch）**

- 常驻守护进程订阅研发流事件：issue 更新 / 指派、CI 失败、PR 评论提及、审批超时；
- 复用 v2.0 webhook 基建（GitHub/Jira/CI 已接入），新增**事件归一化**：异构平台事件 → 统一 `DevelopmentEvent`（类型 + 仓库 + 对象 + 上下文）；
- 提供轮询兜底（webhook 不可达时），保证事件不丢失。

**A2 智能触发器（Trigger）**

- 配置化触发规则：`事件模式 → Run 模板`（如"CI 失败标签 `forgemind:fix` → 诊断 Run"、"issue 标签 `forgemind:build` → 需求 Run"）；
- 触发器决定：是否触发、用什么 Run 模板（复用 v1.0 DAG 拆解）、优先级、冷却时间；
- **事件去重与防风暴**：同对象事件合并、冷却窗口、全局速率限制，防止自动 Run 连环触发。

**A3 自主闭环（Act）**

- 触发后的 Run 执行沿用 v1.0 DAG（无人在场的执行链路与有人在场完全一致）；
- 完成后自动回写：诊断 Run → PR 评论总结；修复 Run → 创建 PR（复用 v2.0 GitHub 集成）；
- 结果回灌 v0.5 `LayeredMemory`（教训沉淀），主动模式"越跑越懂项目"。

**A4 无人值守安全护栏（Guardrail）**

- 主动触发的 Run 必须有**更严格**的审批语义：无人确认的起点，风险动作默认升一级审批（`低→中`、`中→高`）；
- 动作白名单：主动模式只能使用配置允许的工具/命令集合（修复类 Run 默认禁止动数据库、发布等动作）；
- 全链路审计不变：`actor` 标记为 `agentic`，谁批准、批了什么，全部可追溯可回滚。

### P1（已实现）

**A5 受限协作（多 Agent 协商的收敛版）**

- ARCH 方案冲突、REVIEW 连续驳回与 DAG 跨任务 Artifact mismatch 触发 `Proposal → Counter → Decision` 三轮有界协商；
- 协商产出结构化 `DecisionRecord` 并写入 L3；无共识或超时升级审批，**不引入自由对话拓扑**。

**A6 自动修复闭环**（CI 失败的完整闭环）

- 从"诊断 Run"升级为"诊断 → 修复 → REVIEW/TEST 强制门禁 → PR"自动链路；授权仓库、工具/命令白名单与风险升级共同约束修改范围。

## 4. 已落地的形态决策

| 决策点        | 方案 A                                       | 方案 B                  | 建议                                                 |
| ------------- | -------------------------------------------- | ----------------------- | ---------------------------------------------------- |
| 运行形态      | 守护进程常驻（webhook + 轮询兜底）           | 定时任务（cron 批处理） | **A**：事件驱动是主动性的本质，轮询只做兜底          |
| 触发规则      | 配置化规则引擎（声明式，复用 v2.0 策略配置） | 代码内硬编码            | **A**：规则与策略同级治理，可审计可变更              |
| 主动模式安全  | 审批升一级 + 动作白名单 + 全量审计           | 完全自治（无审批）      | **A**：主动不等于失控，"人审批 + 系统执行"是产品底线 |
| 多 Agent 协商 | 三轮有界结构化协议（编排者仲裁）             | 自由对话拓扑            | **A**：已实现可审计协议；自由协商保持非目标          |

## 5. 非目标（本轮不做）

- 不做完全自治：主动触发的 Run 仍受审批门禁约束，风险动作必须人工批准；
- 不做自由多 Agent 协商（A5 已实现三轮有界协议，开放拓扑保持非目标）；
- 不做跨企业 SaaS / 多租户云端托管；
- 不重写 v0.2–v2.0 已验证的编排、安全、记忆、集成内核——本轮是"加上主动性外衣"，不是"换内核"。

## 6. 演示验收标准（DoD）

给定一个演示环境（GitHub 风格仓库 + CI 失败 + 有标签 issue），必须同时满足：

- [x] CI 失败事件到达 → 自动触发诊断/修复 Run → 完成后回写 CI 或关联 PR；
- [x] 带触发标签的 issue → 自动触发需求 Run → 推送独立分支并产出 PR；
- [x] 同事件重复推送不重复触发（delivery 去重 + 冷却 + dispatcher 幂等生效）；
- [x] 主动模式的高风险动作被审批门禁拦截，`actor=agentic` 决策全量入审计；
- [x] 主动 Run 与手动 Run 复用 `runForgeMind/runDagForgeMind`，编排、门禁、沙箱行为一致；
- [x] `npm run check` 全门禁通过，151 项测试覆盖 v0.2-v3.0 回归（本地 148 通过、3 项真实依赖 smoke 条件跳过）。

## 8. 风险与评审要点

1. **自动行动失控是头号风险**：主动 Run 无人确认起点。处置：审批升一级 + 动作白名单 + 速率限制 + 全量审计（A4），宁严勿松。
2. **事件风暴 / 幽灵触发**：一条 CI 失败被多次广播、或修复触发新失败形成连环。处置：去重 + 冷却 + 触发收敛（同对象一个 Run），防连锁。
3. **AI 修了不该修的（scope 蔓延）**：修复 Run 改动超范围引入新缺陷。处置：REVIEW/TEST 强制门禁 + 仓库/工具/命令白名单 + 高风险动作默认禁做。
4. **成本失控**：自动 Run 无节制消耗 token / 沙箱资源。处置：复用 v2.0 I4 配额治理，主动模式配额单独设限。
5. **协调成本**：多 Agent 协商可能违背"编排者决策"主线。处置：A5 仅运行三轮有界协议并由框架仲裁，自由协商保持非目标。
