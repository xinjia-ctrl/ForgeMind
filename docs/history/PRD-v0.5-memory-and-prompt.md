# ForgeMind 第五轮产品企划（PRD v0.5 — 记忆与提示词工程）

> 迭代：第五轮 — 记忆增强 + 上下文/提示词工程
> 前置：v0.4 已实现（生产级安全与沙箱，45/45 测试通过）
> 状态：已实现（61/61 测试通过，`npm run eval` 4/4 场景通过）

---

## 1. 企划定位

产品已有可信闭环（v0.2）与可观测报告（v0.3）。但四项"智能度"评估暴露了真实短板：**系统每次 Run 都是"失忆"的**——不记得项目约定、不记得上次决策、不记得失败教训；上下文投喂靠猜；提示词不可版本化、不可评测、解析靠字符串正则。

**本轮目标**：从"能跑闭环"升级为"越用越懂项目"——把记忆、上下文、提示词三块从"能用的状态"打磨到"可解释、可复用、可评测"的工程状态。

## 2. 现状诊断（对照代码，四项评估确认）

| 维度           | 当前分 | 代码实证                                             | 核心问题                                                        |
| -------------- | ------ | ---------------------------------------------------- | --------------------------------------------------------------- |
| 单次运行记忆   | 3/5    | `TaskContext` 不可变 + `artifacts` 摘要              | 阶段间只传摘要，无过程细节，返工时"只带反馈一句话"              |
| 跨任务长期记忆 | 0.5/5  | `NoopMemoryProvider`，仅接口                         | `remember`/`recall` 是空实现，每次 Run 完全失忆                 |
| 上下文工程     | 3/5    | `TokenBudget` + 摘要 + 文件截断                      | CODE 阶段 `glob("**/*")` 后 `slice(0,8)` 粗暴投喂，无相关性排序 |
| 提示词工程     | 2.5/5  | system prompt 内嵌字符串、`parseJsonObject` 正则解析 | 无版本号、无评测集、非原生结构化输出                            |

## 3. 功能规划

### P0（本轮必做）

**F1 分层记忆（缺陷 2：0.5 → 4.0）**

记忆按生命周期与作用域分四层，由 `LayeredMemory` 容器统一承载，各层独立演进：

| 层              | 记什么                         | 载体                                                 | 何时用                              | 状态    |
| --------------- | ------------------------------ | ---------------------------------------------------- | ----------------------------------- | ------- |
| **L1 工作记忆** | 当前 Run 的决策与过程          | `TaskContext`（不可变）+ 阶段产物                    | 所有阶段装配                        | ✅ 已有 |
| **L2 情景记忆** | 历史 Run 的事件轨迹            | `EventLog` JSONL（已存在，零新增基建）               | 新 Run 前查"同类需求上次怎么失败的" | ⏳ 补强 |
| **L3 项目记忆** | 项目约定 / 架构决策 / 失败教训 | 仓库内 `.forgemind/memory/` 结构化 JSON，随 Git 演进 | PLAN/ARCH/CODE 注入                 | ⏳ 实装 |
| **L4 语义记忆** | 跨项目知识                     | 向量库（Phase 4，接缝预留）                          | 未来                                | ⏸       |

- **L2 情景记忆补强（本轮低成本高价值）**：复用已有 `EventLog`，按需求关键词 + 结果状态（成功/失败）检索历史 Run——"上次这个需求在 REVIEW 被驳回，原因 X"直接注入上下文，比只记技术栈更有说服力。
- **L3 项目记忆实装**：`remember` 用**确定性规则投影**提取（ARCH 的 `decisions[]/files[]` → 决策条目；`gate.rejected.feedback` → 教训条目），**不靠 LLM 总结**，可复现可审计。`recall` 按 `tags` 精确命中 + 关键词重叠打分。
- **分层容器接口**：`MemoryProvider.recall(query)` 带 `scopes`（working/episodic/project/semantic），记忆不串味；`semantic` 层为 null 时跳过不报错。
- **记忆可见**：`memory.recalled` / `memory.stored` 事件进入 EventLog，报告展示"本次 Run 用了哪层记忆、命中依据是什么"——记忆不是黑盒，是可审计的事实。
- **产品红线**：记忆**只读注入**，不修改用户代码；记忆文件需用户确认后才落盘（尊重仓库洁癖）。
- **为何能到 4.0 而非 3.5**：四层分层 + 情景记忆复用现有日志 + 项目记忆确定性提取 + 覆盖 + 全链路可见，构成完整记忆体系；向量库只提升 L4 检索精度，不阻塞分层落地。

**F2 提示词版本化（缺陷 4：2.5 → 4.0）**

- 每个 Agent 的 system prompt 从内嵌字符串抽离为**带版本号的资源**（如 `prompts/plan.v1.md`），用版本常量引用。
- **模板统一结构**（五个固定小节）：
  ```
  [角色与职责] [输入契约摘要] [约束与边界] [输出 JSON Schema] [成功判据]
  ```
  用 `{{placeholder}}` 简单插值，零依赖（遵守"零第三方运行时依赖"底线），不引模板引擎。
- 每次 `llm.called` 事件记录 `promptVersion`，报告可展示"这次 Run 每个 Agent 用了哪个版本的提示词"。
- **回归护栏**：配合 F5 评测集，任何 prompt 改动必须过评测，禁止无评估的静默替换。
- **用户价值**：提示词可改动、可对比、可回退，演示时可展示"同需求不同版本提示词的效果差异"。

**F3 原生结构化输出（缺陷 4：3.5 → 4.5）**

- 用模型的原生结构化能力（`response_format` / JSON mode / tool calling）替换 `parseJsonObject` 字符串正则解析。
- 目标：解析失败率显著下降（当前偶发 "Agent response is not a JSON object" 导致整 Run 失败）。
- 保留校验层 `validation.ts`（契约不变，只是产出路径更稳）。

### P1（本轮力争，可延后）

**F4 上下文相关性装配（缺陷 3：3 → 4.5）**

- **上下文来源分层（L0-L3）**：
  - **L0 核心契约**（必给，不参与预算争抢）：requirement + plan.summary + architecture.summary；
  - **L1 检索上下文**（CODE）：按相关性选择的文件/片段；
  - **L2 记忆上下文**（PLAN/ARCH）：recall 命中的项目约定；
  - **L3 返工上下文**（返工时）：gate.feedback + 上次失败证据 + diff 摘要。
- **装配纯函数化**：从 Agent 内嵌的 `collectWorkspaceContext` 抽离为 `Context Assembler`（输入 ctx + 检索结果 → 输出 `PromptInput`，含 contextFiles 来源标记 + token 统计），可单测、可审计。
- **选择策略**：弃用 `glob("**/*") + slice(0,8)`，改为 **ARCH 预期文件优先 → 需求关键词相关性排序 → grep 命中片段优先（整文件兜底）**。
- **上下文审计视图**：报告新增"每阶段实际注入内容"面板（文件清单、片段来源、token 分布），证明"投喂的是经过选择的内容"——这是上下文工程可信度的直接证据。
- 保留预算约束（TokenBudget 是底线，只换"选什么"，不换"给多少"）。
- **为何能到 4.5**：L0-L3 分层 + 相关性排序 + 检索优先 + 可见性齐备，即构成可解释的上下文装配链路；"动态预算"留作加分项不阻塞。

**F5 提示词评测集（缺陷 4：→ 4.5）**

- 建立固定评测集（3-5 条代表性需求 × 断言：门禁通过、结构输出合法、无越权工具调用）。
- 用 `FakeChatProvider` 做确定性回归（防提示词改动静默回退），真实模型做抽样冒烟。
- 纳入 `npm run check` 可选的 `npm run eval`。
- **进阶**：评测输出**对比报告**（版本 A vs B 的通过率 / 返工轮次 / token 成本），直接支撑"提示词工程"的面试叙事。

## 4. 选型决策：记忆方案对比（评审要点）

**结论：分层范式对齐业界（不发明），实现自研轻量（不引依赖）。**

| 候选方案               | 分层范式                                | 形态         | 与本项目约束的冲突                                                        |
| ---------------------- | --------------------------------------- | ------------ | ------------------------------------------------------------------------- |
| **Mem0**               | working/episodic/semantic/procedural    | 库或托管     | 引库/引服务，打破"运行时零第三方依赖"底线；数据在外部，违背"仓库即事实源" |
| **Letta (MemGPT)**     | core memory + archival + recall         | 平台/库      | 平台级能力超出本项目场景；记忆不随 git 演进                               |
| **Zep (Graphiti)**     | 时序知识图谱                            | 平台/服务    | 需要外部服务 + 关系推理，过度设计                                         |
| **LangGraph Memory**   | checkpointing + semantic search + store | 框架内置     | 依赖 LangGraph 生态，本项目自研编排                                       |
| **本项目（自研轻量）** | working/episodic/project/semantic       | 本地分层容器 | 无冲突：数据在 git+JSONL，符合红线                                        |

**决策理由**：

1. **范式不发明**：四层分层直接对齐 Mem0/Letta 已验证范式，规避"自创记忆理论"风险。
2. **实现不引依赖**：本项目真实场景只有"跨 Run 项目记忆 + 情景检索"，用不到平台能力；引外部依赖属过度设计。
3. **本地即事实源**：记忆落 `.forgemind/memory/` + 复用 EventLog，可审计、可回退，是产品红线而非负担。
4. **迁移接缝**：接口对齐业界（`recall(query, scopes)`），未来可换向量库 / Mem0 只动 L4，不重构。
5. **面试叙事**：能讲清"为何不直接用成熟库"本身就是架构师判断力的证明。

## 5. 非目标（本轮不做）

- 不做跨项目全局记忆（本轮是"项目级记忆"，跨项目语义检索仍为 Phase 4 后续）。
- 不做向量库（结构化 JSON + 关键词检索足以支撑演示，向量库是接缝处可换的实现）。
- 不做提示词自动化调优（Auto-Prompt 优化器，超出本轮工程范围）。
- 不改变 Orchestrator 控制流与门禁语义。

## 8. 风险与评审要点

1. **记忆污染风险**：记忆注入必须"只读、可审计、可回退"，否则用户不敢用。落盘需确认、注入需可见。
2. **结构化输出兼容性**：`response_format` 依赖具体模型与厂商协议，需在 `ChatProvider` 接缝处做能力探测与优雅降级（不支持则回退正则解析）。
3. **提示词版本化不回归**：必须有评测集兜底，否则"改进"可能静默变差。
4. **上下文相关性是双刃剑**：排序策略误伤关键文件会引入新缺陷。P1 阶段先做"ARCH 预期文件优先"，关键词相关性排序需实测后收敛。
