# ForgeMind 产品需求文档（PRD v1.0 — 生产可用）

> 版本：v1.0（第七轮 — 从演示到生产可用）
> 前置：v0.4 沙箱/审批已实现、v0.5 记忆/提示词工程及兼容性增强已实现（64/64 测试通过）
> 状态：V1 DAG 内核、V2 多仓库已实现；V3 Web 工作台规划中
> 对齐愿景：E1（需求到上线）、E2（审批范式）、E4（研发舰队）

---

## 1. 产品定位（本轮视角）

v0.2-v0.5 已经把"单条需求走通全链路"打磨到生产级单点能力：安全沙箱、审批网关、四层记忆、上下文工程、提示词评测。但产品形态仍是**命令行单任务工具**：一次 Run 处理一个需求、作用于一个仓库、按固定顺序执行。

**本轮要解决的核心问题**：从"单任务 CLI 工具"升级为"可并行、可接入真实研发流程的研发平台"——

- **并发**：一个需求拆解为多个可并行的 Agent 任务（前端/后端/测试），DAG 编排而非固定顺序；
- **多仓库**：跨仓库编排，一个需求可同时作用于多个仓库；
- **工作台**：提供 Web 界面，看板 + 审批 + 结果，替代纯命令行。

这是 VISION 中"研发舰队"（E4）与"需求到上线"（E1）的落地，也是从"演示 Demo"到"敢接入团队流程"的分水岭。

## 2. 目标用户与场景

| 场景         | 用户               | 核心诉求                                                         |
| ------------ | ------------------ | ---------------------------------------------------------------- |
| 真实团队接入 | 研发团队           | 一个需求拆成多个任务并行跑，跨仓库协作，结果集中管理             |

## 3. 核心能力

### P0（本轮必做）

**C1 DAG 并发编排**

- 需求 → PM Agent 拆解为**多任务计划**（任务间有依赖关系，构成 DAG，而非顺序列表）；
- Orchestrator 升级为 DAG 调度器：无依赖任务并行执行，有依赖任务等待前驱完成；
- 每任务独立 `runId`（子 Run），共享父 Run 的 `TaskContext` 决策与记忆；
- 全链路门禁语义不变：每个任务仍需过 REVIEW/TEST 门禁。

**C2 多仓库支持**

- 需求可声明涉及多个仓库（`--repos a,b,c`），跨仓库任务并行；
- 每个仓库独立分支、独立沙箱、独立测试，共享记忆与产物索引；
- 合并策略显式化：跨仓库 commit 后不自动 merge，产出 PR 清单交人类决策。

**C3 Web 工作台（第一版）**

- 只读看板：展示 DAG 实时状态（运行中/成功/失败/等待审批），复用现有 `EventLog` 事件流；
- 审批面板：需审批的高风险动作在工作台展示，一键批准/拒绝（复用 v0.4 审批网关）；
- 结果页：复用 v0.3 报告渲染，任务完成后内嵌展示。

### P1（本轮力争，可延后）

**C4 配置化团队策略**：DAG 拓扑规则、仓库白名单、审批分级（风险等级 → 自动/需审批）通过配置文件声明，不写死在代码。

**C5 CI 集成**：收到 GitHub/GitLab push/PR 事件触发 ForgeMind Run（webhook），"改代码 → 自动分析 → 出 PR"闭环。

## 4. 关键形态决策（待评审）

| 决策点     | 方案 A                                           | 方案 B                              | 建议                                                              |
| ---------- | ------------------------------------------------ | ----------------------------------- | ----------------------------------------------------------------- |
| DAG 引擎   | 自研轻量调度器（复用现有 Orchestrator + 依赖表） | 引外部工作流引擎（Temporal/Argo）   | **A**：场景只有"任务级依赖"，外部引擎过度设计，且破坏零依赖底线   |
| Web 工作台 | 自研静态页 + 事件订阅（Node http + SSE）         | 引入前端框架（React/Vue）+ 后端框架 | **A**：复用现有纯函数报告/事件模型，静态生成 + SSE 即可，不引框架 |
| 并发粒度   | 阶段级并发（同一阶段多任务并行）                 | Run 级并发（多 Run 并行）           | **A**：先做阶段级，编排可控、调试简单                             |

## 5. 非目标（本轮不做）

- 不做多 Agent 自由协商（仍为编排者决策，DAG 只是执行拓扑）。
- 不做长期记忆语义检索升级（L4 向量库，Phase 4 后续）。
- 不做云端托管 / SaaS 化 / 多租户。
- 不做主动式 Agent（盯 issue、回 PR 评论，v3.0）。

## 6. 演示验收标准（DoD）

给定一个跨仓库演示需求（涉及 2 个仓库、可拆 3 个任务），必须同时满足：

- [x] 需求自动拆解为 DAG 任务，无依赖任务**并行**执行（有并发证据：时间戳重叠）；
- [x] 依赖任务按序执行（前驱成功后后继才开始）；
- [x] 每个任务独立分支、独立沙箱、独立测试，各自过门禁；
- [x] 跨仓库全部成功后才产出 PR 清单，不自动 merge；
- [ ] Web 工作台实时展示 DAG 状态，审批动作可在工作台完成；
- [ ] 任务结果页内嵌报告（复用 v0.3）；
- [x] 原有 64 个测试全部通过，单任务模式行为不回归。

## 8. 风险与评审要点

1. **并发引入的竞态**：多任务同时写工作区/共享文件会踩踏。每个任务必须独立沙箱 + 独立工作区快照，交叉产物通过显式 Artifact 引用，禁止直接共享可变目录。
2. **DAG 调度复杂度**：任务失败传播、超时、死锁（循环依赖）需显式规则。MVP 只支持 DAG（无环），循环依赖在拆解阶段即报错。
3. **Web 工作台是范围陷阱**：容易越做越大。P0 只做只读看板 + 审批面板 + 结果页，编辑/配置界面一律延后。
4. **可观测性放大**：并发后事件量暴增。事件模型加 `runId + taskId` 两级索引，报告/回放按任务过滤。
5. **CI 集成（P1）依赖外部平台**：需 webhook 鉴权与仓库权限设计，若超预算则本轮不做，明确划入 v1.1。
