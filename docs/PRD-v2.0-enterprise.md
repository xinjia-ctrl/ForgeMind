# ForgeMind 产品需求文档（PRD v2.0 — 企业平台）

> 版本：v2.0（第八轮 — 从研发工具到企业平台）
> 前置：v1.0 已规划（DAG 并发 + 多仓库 + Web 工作台）
> 状态：I1 企业集成、I2 RBAC、I3 有界查询/导出均已实现；实时工作台明确不属于 v3.0 交付
> 对齐愿景：E2（审批范式）、E3（记忆资产）、E5（可观测即信任）

---

## 1. 产品定位（本轮视角）

v1.0 让 ForgeMind 能"并行跑、跨仓库、有工作台"，本质仍是**单个研发团队内部工具**。v2.0 要解决的是：让 ForgeMind 成为**可以被整个企业信任和治理的研发基础设施**——

- **接入企业系统**：与 Jira/CI/代码托管平台互通，需求从 issue 来、结果回到 PR/流水线；
- **权限与治理**：谁能发起 Run、谁能批准、谁能看数据，全部受控可审计；
- **主动式能力**：不再"等人给需求"，而是盯住 issue / CI 失败，主动触发研发闭环。

这是 VISION 中"企业接入层"（GitHub/Jira/CI + 审计报表 + 权限治理）与"研发操作系统"（v3.0 主动式 Agent）的前置：**v2.0 做接入与治理，v3.0 做主动性**。

## 2. 目标用户与场景

| 场景     | 用户               | 核心诉求                                               |
| -------- | ------------------ | ------------------------------------------------------ |
| 企业落地 | 平台团队 / 管理员  | 系统接入现有研发工具链，权限可控，全量可审计           |
| 研发团队 | 开发者 / Tech Lead | 需求从 Jira 来，结果自动回 PR/CI，少一次手动搬运       |
| 管理者   | 研发负责人         | 全局审计报表：Agent 干了什么、花了多少 token、质量如何 |
| 面试展示 | 候选人             | 展示"企业级工程"：集成、权限、治理、合规设计           |

## 3. 核心能力

### P0（本轮必做）

**I1 企业系统集成**

- **Jira/需求系统**：从 issue 拉取需求作为 Run 输入，完成后把结果（PR 链接 / 失败报告）回写 issue 评论；
- **代码托管**：PR 创建 / 评论（v1.0 已产出 PR 清单，v2.0 自动创建与评论）；
- **CI 联动**：Run 完成后触发目标仓库 CI，把结果回传。

**I2 权限与治理（RBAC）**

- 角色：`viewer`（只读）/ `developer`（可发起 Run）/ `approver`（可批准高风险动作）/ `admin`（配置策略与权限）；
- 作用域：仓库级 + 团队级权限，`deny-by-default`，未授权即拒绝；
- 审批分级：按风险等级映射到角色（`低→自动`、`中→developer 可批`、`高→approver 必批`）。

**I3 全量审计报表**

- 企业级审计面板：按人 / 仓库 / 时间维度检索所有 Run、审批决策、命令执行、token 消耗；
- 导出能力：审计数据可导出（CSV/JSON），满足合规归档。

### P1（本轮力争，可延后）

**I4 预算与配额治理**

- 每团队 / 每仓库设月度 token 配额、并发上限、沙箱资源上限；
- 超配额自动降级（排队 / 拒绝），支撑成本治理。

**I5 多租户 / 工作空间**

- 按团队隔离数据（Run、记忆、报告），记忆不跨租户串味。

## 4. 关键形态决策（待评审）

| 决策点   | 方案 A                     | 方案 B                  | 建议                                                           |
| -------- | -------------------------- | ----------------------- | -------------------------------------------------------------- |
| 集成方式 | Webhook + API（被动集成）  | SDK/客户端嵌入          | **A**：标准 webhook + REST，零侵入，先覆盖 GitHub/Jira 两平台  |
| 权限模型 | 自研 RBAC（文件/配置驱动） | 接企业 SSO（OIDC/SAML） | **A 起步**：先自研 RBAC 保证可用，OIDC 作为 P1 接缝            |
| 审计存储 | 扩展现有 JSONL + 索引      | 引入数据库              | **A**：审计基于事件事实源，JSONL + 只读索引足够，DB 属过度设计 |

## 5. 非目标（本轮不做）

- 不做多 Agent 自由协商（v3.0）。
- 不做主动式 Agent（盯 issue / 修 bug / 回 PR 评论，v3.0）。
- 不做云端 SaaS / 全托管部署。
- 不重构 v0.x-v1.0 已验证的编排、安全、记忆内核——v2.0 是"加外层"，不是"换内核"。

## 6. 演示验收标准（DoD）

给定一个企业演示环境（GitHub 风格仓库 + Jira 风格 issue），必须同时满足：

- [x] 从 issue/Webhook/Poller 拉取需求 → 触发 Run → 完成 → 自动创建 PR → 评论回写 issue；
- [x] 三类角色权限生效：viewer 不能发起 Run，developer 不能批准高风险动作；
- [x] 审批分级生效：高风险动作需 approver，决策全量入审计；
- [x] 审计 CLI 可按人/仓库/时间检索并导出 JSON/CSV；
- [x] `npm run check` 全门禁通过，151 项测试覆盖既有单任务/并发模式回归。

## 8. 风险与评审要点

1. **集成范围膨胀**：Jira/GitHub/CI 每个都是深坑。MVP 只做"读 issue / 写 PR + 评论"两条最小路径，其余 API 能力一律延后。
2. **权限粒度是安全命门**：RBAC 做不好就是安全漏洞。默认 deny + 最小权限 + 全量审计，宁严勿松。
3. **审计数据规模**：企业多租户后事件量大。审计查询需只读索引 + 时间窗口限制，不做全量实时检索。
4. **多租户记忆隔离**：记忆串味是数据事故。workspace scope 必须强制隔离，且审计可见。
5. **P1 超预算即砍**：配额治理 / 多租户若拖累 P0，明确划入 v2.1，不阻塞 I1-I3 交付。
